# 业务流程梳理方法(第 10 维:流程层,横切所有功能点)

单功能点用例是"点",业务流程用例是"线"。**很多缺陷只在线上暴露**:
数据从 A 功能传到 B 功能时丢失/变形、权限变更后全链路不同步、
中断恢复后重复执行。功能点用例全过 ≠ 业务正确。

## ⓪ 第一步永远是:生成「业务理解文档」给用户核对(门槛步骤)

**理解错了,后面所有用例全错。** 所以在一切梳理之前,先把 AI 自己的
业务理解写成文档,**用户核对纠偏确认后才继续**。文档规则:

1. **三色置信度标注**(核心机制,不许省):
   - ✅【依据】有明确来源(引用 PRD 原文/原型Frame/接口字段,注明出处)
   - 🔶【推测】素材没直说,我按常理推的(写明推测依据)
   - ❓【不懂】看不懂/矛盾/素材缺失(明确说缺什么)
2. **主动暴露认知盲区**:宁可多列 ❓ 也不装懂;❓ 数量是理解质量的反向指标
   🔶【推测】只允许存在于理解文档中供核对,**核对通过前禁止流入任何用例**;
   用户未拍板的 ❓ 在用例中一律预期留空标【待确认】
3. **用户核对方式**:逐节问"对不对/哪里不对",用户纠偏后回填并升级为 ✅
4. **核对后的理解档案落盘**:存 `<项目>/docs/business-understanding.md`,
   下次同项目直接复用+增量更新,不重新问

### 业务理解文档模板(7 节)

```markdown
# <产品> 业务理解(待核对)
> 生成日期 | 素材:原型xx/PRDxx/接口xx/合约xx

## 1. 业务是什么
一两句话:这个产品让谁、通过什么、得到什么价值。
🔶【推测】... 或 ❓【不懂】商业模式看不清,需确认

## 2. 角色与权限
| 角色 | 能做什么 | 不能做什么 | 依据 |
每个角色一行;无权部分是权限用例的直接来源。

## 3. 核心业务主线(价值链)
创建 → 配置 → ... → 终态(文字箭头图)
每环标注:对应功能点/页面/接口。有几条并行主线就画几条。
🔶 主线顺序是我按xx推测的,需确认

## 4. 关键业务规则(逐条)
| 编号 | 规则(我的复述) | 原文依据 | 置信度 |
R1: 下单立即扣款,不等开盘 | PRD§xx"受理成功立即扣除" | ✅
R2: ... | 无直接依据,按行业惯例推测 | 🔶

## 5. 状态与流转
核心实体的状态机:实体名 | 状态枚举 | 合法流转 | 终态
(状态枚举从接口响应/文档收集,流转部分常需推测)

## 6. 数据怎么流(跨功能传递链)
上游产出 → 下游消费 的链路清单(资金流/状态流/权限流)

## 7. 我不确定的点(汇总)
全部 ❓ 与重要 🔶 集中列出,逐条请用户裁决。
```

## 一、梳理四步(理解文档确认后做)

### 1. 识别业务主线(产品的价值链)
把产品核心业务串成主线,每环=一个功能点或功能组。
例(代币经济学):创建代币 → 配置持有条件 → 关联证书 → 编辑分配计划 →
发布分配 → 增发 → 解锁领取
例(交易类):注册登录 → 入金 → 报价下单 → 结算 → 佣金分配 → 出金
**产出:主线图(文字箭头图即可)+ 每环对应的功能点编号。**

### 2. 识别角色与其旅程
| 角色来源 | 典型角色 |
|---|---|
| 权限差异 | Owner/协作账户/普通用户/无证用户/只读管理员/超管 |
| 状态差异 | 新用户(空态)/活跃用户/被停用用户/无余额用户 |

每个角色走一遍主线,标出**断点**(该角色在哪一环被拦/走不同分支)。
例:无证账户 → 在 发布/增发/领取 三环全被拦(这就是一条 E2E 用例)。

### 3. 追踪跨功能点的状态传递(最重要)
列出"上游产出 → 下游消费"的传递链,每条链都是用例:
| 传递链 | 断言什么 |
|---|---|
| 下单 → 结算 → 账本分录 → 余额 | 每一跳金额一致,守恒 |
| 下单结算 → 佣金计算 → 团队量 → VIP等级 → 新单费率 | 传递不丢失不延迟变形 |
| 创建 → 详情页 → 列表页 → 我的代币 | 同一数据多处展示一致 |
| 后台改配置 → 前台行为 → 历史数据不受影响 | 生效边界正确 |
| Owner转移 → 我的列表 → 各操作权限 → 审计归属 | 全链路同步生效 |

### 4. 提炼业务不变式(横切断言)
跨功能的"恒真"陈述,任何流程用例都应顺带断言:
- 守恒类:总资产变化 == 所有分录之和;发射总量 == 创建+增发-销毁
- 唯一类:一个代币同一时刻只有一个 Owner;同一业务键全链路只生效一次
- 互斥类:已发布计划不可再编辑;终态订单不可再操作

## 二、流程用例的 6 种类型(每条主线至少覆盖前 3 种)

| 类型 | 模板 | 优先级 |
|---|---|---|
| **全生命周期 E2E** | 正常角色把主线从头走到尾,每环断言状态与数据 | P0 |
| **全程拦截 E2E** | 无权限角色依次尝试主线每环,全部被拦且零副作用 | P0 |
| **权限变更 E2E** | 中途转移 Owner/停用账户,验证**后续每一环**同步失效/生效 | P0 |
| **中断恢复 E2E** | 提交后断网/超时 → 恢复:不重复执行、状态可查询、数据不丢 | P1 |
| **数据往返 E2E** | 多步表单:下一步→返回→再进,已填数据保留不错位 | P1 |
| **并行流 E2E** | 两个角色/两条业务并行推进,互不干扰不串数据 | P1 |

## 三、流程用例写法(与功能点用例的区别)

- 标题带旅程:`端到端-合规代币全生命周期` / `旅程-新用户从注册到首单`
- 步骤允许跨页面跨模块(编号长步骤,每步注明在哪一环)
- 预期按环编号:`1-3. 各环成功且数据正确;4. E 被拒(无凭证)`
- 前置要准备**多角色多状态**的完整数据矩阵(谁持有什么)
- E2E 失败时能定位到环:预期按环写就是为了这个

## 四、实战教训

- 端点覆盖 100% ≠ 业务正确:实测 107/107 端点全过,仍在"佣金→团队量"链上抓到级差算错
- 单点断言要升级为链式断言:不只"这一环对",要"上一环的输出在本环还认"
- 流程用例最怕环境断裂(余额不够/次数用尽):前置里写清数据准备方法,
  断裂时明确标"环境阻塞"而非跳过
- 旅程命名从用户视角(不是接口视角):"新用户首访看到空态"而不是"GET /orders 返回[]"
