# PRD 分析方法

## 优先级:验收矩阵 > 规则句式 > 章节叙述

1. **先找「验收矩阵」章节**(表格,列常为 场景/操作/预期):这是产品方自己定义的
   验收基准,**每行至少映射 1 条用例**;矩阵没覆盖的章节内容按下面方法补充。
2. **规则句式扫描**(全文 grep 这些词):
   - 禁止/不得/不允许/不能 → 负向用例(做了必须被拒+零副作用)
   - 必须/应当/唯一/至少 → 正向强断言(唯一性/至少性单独成条)
   - 仅限/只有/除外 → 权限/条件分支用例
   - 恰好/等于/超过/不足 → 等值边界用例(相等时归哪边必须明确)
   - 逐笔/四舍五入/精度 → 精度用例(.xx5 边界样本)
3. **字段字典**章节是边界值金矿:每个字段的最大/最小/精度/格式 → 维度2直接展开。
4. **状态类描述**(枚举/流程图文字)→ 维度8状态机:列出全部状态,补非法跳变。

## 版本规则

- 多个「修订」章节按**最新日期覆盖旧规则**(常见:同名修订出现 2-3 次)
- 修订只写差异,旧章节其余部分仍有效;冲突以修订为准并在用例备注标注"依据:xx修订"

## 模糊词检测(扫到必进悬置项)

PRD 里的模糊量词/形容词没有可判定性,逐个摘出问用户要量化定义:

| 模糊词模式 | 要澄清成什么 |
|---|---|
| 快/迅速/流畅 | 具体秒数/帧率目标 |
| 大量/高并发/海量 | 具体条数/QPS/用户数 |
| 灵活/智能/友好 | 具体行为差异(相对什么灵活) |
| 尽量/原则上/一般 | 例外条件是什么,谁触发 |
| 简单/轻松支持 | 对比基准 |
| 少量/适度 | 具体数量级 |
| 等/之类/例如 | 开放枚举要闭合:全列还是任一 |

## 事件流三段式(RUP 场景法,叠加在业务主线上)

业务理解文档确认的每条主线,再强制拆三层(备选流是最容易漏的):

```
主流程 : 一切正常的Happy Path(=全生命周期E2E)
备选流 : 每个可分支决策点的另一条合法路(余额不足走充值入口/
         方向不符走手搓确认/未预约走0次提示)
异常流 : 每步可能失败的中断(超时/断网/权限失效/并发冲突/数据不存在)
```
拆法:沿主线逐步问"这步还能合法地走别的路吗?"(→备选流)、
"这步会怎么失败?"(→异常流);每条备选/异常流=1条用例,失败流必带零副作用断言。

## 外部依赖识别(输入盘点时必做)

列出产品依赖的外部系统,每个依赖 3 问(答不出→悬置):
| 依赖 | 它挂了产品表现? | 数据可从它官方源核对吗? | 有降级/缓存吗? |
| 行情源 | ... | 实测曾不可对账(D11教训) | ... |
第三方支付/短信/链上节点/CDN 同理。依赖不可核对时,相关用例标
"外部依赖不可验证",不写数值断言。

## 输出物

| 产物 | 形式 |
|---|---|
| 规则条款清单 | 编号 R1/R2...:原文摘录 + 章节位置 |
| 功能点候选 | 与原型/接口功能点合并去重 |
| 悬置项 | PRD 没写的(触发方式/数值来源/异常文案) |

## 实战教训

- PRD 写的数值(赠送额/费率)是**文档基线**,用例预期写"按配置动态推导",
  PRD 数值只出现在 WARN 断言——环境配置随时会改。
- PRD「验收矩阵」19 条实测只覆盖到 11 条时,剩余条目不是放弃而是标注
  "需环境/时机/注入"——诚实标注比假覆盖有价值。
- PRD 与实现冲突时:按实测行为写断言,差异记为缺陷候选,不硬套 PRD。
